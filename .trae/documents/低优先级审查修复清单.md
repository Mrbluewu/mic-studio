# 低优先级审查修复清单

> 承接 `高优先级审查修复清单.md`（H-1～H-3 已完成）与 `中优先级审查修复清单.md`（M-1～M-4 已完成）。
> 本清单只收低优先级项：不改变功能行为、风险低、可独立验证。

| 编号 | 状态 | 问题 | 处理 |
|---|---|---|---|
| L-1 | 已完成 | `TapBuffer::read_latest` 在 `dst == nullptr && frames == 0` 时仍计算 `dst + offset`，属空指针算术 | `frames == 0` 直接返回 `true`，不触碰指针 |
| L-2 | 已完成 | `apps/engine-cli` 导出 AB 对比音频时忽略 `read_latest` 的失败标志，快照被覆盖时会把新旧数据拼在一起 | 每个 tap 最多重试 4 次（间隔 20 ms），仍失败则沿用最后一次结果 |
| L-3 | 已关闭 | 限幅器天花板硬编码 `-1.0f`（原 M-5） | 决策：提为具名常量 `kLimiterCeilingDb`，行为不变、不新增用户配置 |
| L-4 | 已关闭 | VST3 `in_changes` / `out_changes` 容量固定 64（原 M-6） | 决策：保持 64，接受为饱和降级；单块内 64 个不同参数同时变化实际不可达 |
| L-5 | 未处理（不修） | 队列与 `SpscRingBuffer` 的 `alignas(64)` 触发 C4324 填充警告 | 对齐是有意用于缓存行隔离，为消警告而改动布局会引入伪共享风险 |

## 修复证据

### L-1 `modules/engine/include/engine/tap_buffer.h`

* 改动：在空指针与越界判定之后增加 `frames == 0` 的短路返回 `true`。
* 原因：原逻辑在 `frames == 0` 时会执行 `std::fill(dst, dst + 0, 0.0f)`，`nullptr + 0` 虽不写入但不属于良定义行为。
* 验证：`ms_concurrency_tests` 通过（含空容量、短数据、满容量、多圈与并发用例）；Release 构建无新增警告。

### L-2 `apps/engine-cli/main.cpp`

* 改动：AB 导出取快照处由直接调用改为最多 4 次重试循环，成功即跳出。
* 原因：渲染线程持续写入时 `read_latest` 会因覆盖返回 `false`，此时 `raw`/`processed` 可能混合了不同时刻的数据，导出的对比音频会被误读为"处理劣化"。
* 边界：导出属诊断路径，重试有固定上界且不在音频线程执行；仍失败时行为与原来一致（继续导出），不改变退出码。
* 验证：Release 构建成功；`engine-cli.exe` 正常生成。

### L-3 决策与实施

* 决策：不暴露为用户设置，改为具名常量；-1 dBFS 视为固定输出契约（留 1 dB 余量给重采样与设备端）。
* 实施：`modules/engine/src/audio_engine.cpp` 匿名命名空间新增 `kLimiterCeilingDb = -1.0f`，链路构建处改用它，数值与行为不变。
* 理由：可调项需要同时改 `EngineOptions`、设置面板与持久化三处，收益不足以抵消回归面。

### L-4 决策

* 决策：保持 64，不再处理。
* 依据（代码事实）：`ParameterChanges(maxParameters)` 在槽构造期一次性分配队列，实时路径不分配；`ParameterValueQueue::addPoint` 在同一 `sampleOffset` 上只覆盖不追加，而本实现固定用偏移 0，因此每个参数队列恒为 1 个点，不会在音频线程触发 `vector` 扩容。
* 结论：容量 64 只限制“单块内不同参数数量”，超出时 `addParameterData` 返回空、该参数本块跳过，属已接受的饱和降级。
